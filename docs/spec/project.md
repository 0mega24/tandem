# Project, tooling and Nix (spec)

Copied from the owner's design document, tab "Project, tooling and Nix" (2026-11-17). This is the
record of the spec. Where the repo differs, docs/DESIGN.md "Changes from the spec" says how and why.
`OWNER` is `0mega24`.

This tab locks the project name, structure and tooling. It also adds Nix packaging. The project is
Tandem, and its command is tdm.

## Name, credit and license

Tandem is a new project that is inspired by wtg. It is not a fork, it does not copy wtg code, and
its README credits wtg for the idea.

### Name

The project is Tandem, and the command is tdm. "In tandem" means "together, at the same time": the
repos of a space move together on one branch, and their build systems work as one. The name says
what the tool does without a narrow word such as "worktree" or "Go". Other worktree tools already
use grove, copse and canopy. I found no worktree tool named Tandem, but check GitHub, nixpkgs and
the package registries before the first release.

Naming rule: the command, the plugin prefix and the environment variables use tdm. Everything else
uses tandem. The Generators tab still says wtg; read it as tdm for the command and Tandem for the
project.

| Item | wtg | Tandem |
|---|---|---|
| Command | wtg | tdm |
| Repository and Go module | github.com/geoffamey/wtg | github.com/OWNER/tandem |
| Config file | ~/.config/wtg/config.toml | ~/.config/tandem/config.toml |
| State directory | ~/.local/share/wtg/spaces/ | ~/.local/share/tandem/spaces/ |
| Config variable | WTG_CONFIG | TDM_CONFIG |
| Hook variables | WTG_SPACE_NAME, ... | TDM_SPACE_NAME, ... |
| Plugin executables | — | tdm-gen-<id> |
| Generated-file header | Generated by wtg | Generated by tandem |
| Space-root directory | .wtg/ | .tandem/ |
| Shell helper | wcd | tcd |
| Agent skills | wtg, wtg-setup | tandem, tandem-setup |
| Nix package | — | pkgs.tandem (main program tdm) |

### Migration from wtg

A one-time command, `tdm import wtg`, reads `~/.local/share/wtg/spaces/*.yaml` and the wtg config.
It writes the Tandem state and config, and changes nothing in the worktrees, because the paths stay
the same. It records the hash of each existing go.work, so the ownership check accepts it. The
command does nothing if the wtg directories do not exist.

## Locked project structure

The tree is in docs/DESIGN.md (with the approved additions). The original rules:

1. Only cmd/tdm and tools/* hold package main.
2. All Go code is under internal/. Tandem has no public Go API in version 1. The plugin protocol is
   the public extension point.
3. A generator package may import only internal/gen, internal/gen/urlnorm, the standard library and
   file-format parsers. It must not import cli, state, git or saga. The depguard linter enforces this.
4. A file named zz_generated_*.go, docs/generators.md or schema/config.schema.json is generated. Do
   not edit it. CI fails if make generate changes it.
5. Each generator has the same four files and the same testdata layout. make newgen ID=<id> makes them.
6. The Makefile is the only task runner. Taskfile.yml is removed.
7. AGENTS.md is the agent guide. CLAUDE.md is a symlink to it, so Claude Code and Codex read the
   same file.

## Go tooling

To add a generator, you write one package. go generate then makes the registry, the docs, the
config schema and the config template from the code. Nothing is copied by hand, so the docs and
the code cannot disagree.

### Registration

Each generator registers itself in init(), like a database/sql driver:

```go
// internal/gen/rust/rust.go
package rust

import "github.com/OWNER/tandem/internal/gen"

func init() { gen.Register(Generator{}) }

type Config struct {
    Mode       Mode     `toml:"mode" jsonschema:"enum=auto,enum=patch,enum=workspace,default=auto"`
    Registries []string `toml:"registries" jsonschema:"description=Extra registries to patch"`
}

func (Generator) Meta() gen.Meta {
    return gen.Meta{
        ID:        "rust",
        Languages: []string{"Rust"},
        Manifests: []string{"Cargo.toml"},
        DefaultOn: true,
        Release:   1,
        Config:    Config{Mode: ModeAuto},
    }
}
```

gen.Register panics on a duplicate ID, so a test run finds the error at once. The Generator
interface gets Meta() in place of ID() and DefaultEnabled(). Plan receives the decoded config: each
generator calls gen.DecodeConfig[Config](s.Config).

### What go generate makes

All directives are in one file, internal/gen/generate.go, so they run in a fixed order. make
generate runs go generate ./....

```go
// internal/gen/generate.go
package gen

//go:generate go run ../../tools/genregistry -out all/zz_generated_imports.go
//go:generate go run ../../tools/gendocs -docs ../../docs/generators.md -schema ../../schema/config.schema.json -template ../config/zz_generated_template.toml
```

| Step | Tool | Reads | Writes |
|---|---|---|---|
| 1 | genregistry -out | The directory list under internal/gen/ (with go/parser; it compiles nothing) | all/zz_generated_imports.go: one blank import for each generator |
| 2 | gendocs | gen.All() at run time, through the new imports | docs/generators.md (the table in the Generators tab), config.schema.json, the commented config template for tdm config init |
| — | go tool stringer | type Mode int in each package | zz_generated_mode_string.go |

There are two tools because gendocs imports internal/gen/all. If one tool did both steps, it could
not compile when the imports file names a generator that you deleted. genregistry imports nothing
from Tandem, so it always compiles.

Step 1 also checks each generator directory. It fails when a directory has no init() that calls
gen.Register, or no doc.go, or no testdata/ with the six required cases.

The JSON Schema lets editors complete and check config.toml. Taplo and the Even Better TOML
extension read a `#:schema` line at the top of the file, and tdm config init writes that line.

### Scaffolding a new generator

`make newgen ID=zig MANIFEST=build.zig.zon` runs tools/newgen. It writes the four files and the six
testdata cases from templates that are compiled into the tool with //go:embed. Then it runs make
generate. The new generator compiles, fails its golden tests with a clear message, and shows in
`tdm generate --list`.

### Tool versions

Since Go 1.24, a tool directive in a modfile pins a tool, and `go tool <name>` runs it. wtg already
uses this for gotestsum. Tandem moves the third-party tools into a separate modfile, go.tool.mod,
so that tool dependencies stay out of the program's go.mod. This also keeps the Nix vendorHash small.

| Tool | Where pinned | Use |
|---|---|---|
| gotestsum | go.tool.mod | Test output |
| stringer | go.tool.mod | Enum strings |
| govulncheck | go.tool.mod | Vulnerability check |
| testscript (go-internal) | go.mod (test only) | End-to-end CLI tests |
| golangci-lint, gofumpt, goreleaser, nixfmt | flake.lock | Lint, format, release, Nix format |

The rule: a Go tool that changes generated files or test results is pinned in go.tool.mod. Every
other tool comes from the Nix dev shell.

### End-to-end tests with testscript

The Go command tests itself with text scripts in the txtar format. Tandem uses the same method
through github.com/rogpeppe/go-internal/testscript. Each generator adds one script, for example
internal/cli/testdata/script/new_rust.txtar. The script makes two git repos, runs tdm new, and
compares the generated files. These scripts need git but no language toolchain, so they run in
every CI job.

### Version information

internal/version has Version, Commit and Date. The Makefile and Nix set them with -ldflags -X. When
they are empty (a go install build), Tandem reads them from runtime/debug.ReadBuildInfo.

## External generator plugins

A plugin is an executable in any language that answers two JSON requests. It gives a plan, and
Tandem does the writes, the ownership check and the rollback. This replaces the
`[[generate.custom]]` scripts in the Generators tab, which wrote files themselves.

### Discovery

Tandem uses the kubectl model. kubectl finds a plugin by an executable file name that starts with
`kubectl-` anywhere on PATH, and needs no other configuration (KEP-2379). Tandem finds
`tdm-gen-<id>` in these places, in this order:

1. `[generate] plugin_dirs` in the config
2. `$XDG_DATA_HOME/tandem/plugins/`
3. PATH

The first match wins. A plugin ID must not be the same as a built-in ID. `tdm generate --list`
shows each generator with its source (built-in or the plugin path).

### Protocol, version 1

Tandem runs the plugin with one argument and reads one JSON object from stdout.

`tdm-gen-zig meta` (no stdin):

```json
{
  "protocol": 1,
  "id": "zig",
  "languages": ["Zig"],
  "manifests": ["build.zig.zon"],
  "default_on": false,
  "config_schema": {"type": "object", "properties": {}}
}
```

`tdm-gen-zig plan` (the space as JSON on stdin):

```json
{
  "space": {"name": "my-feature", "root": "/home/me/workspaces/my-feature", "branch": "me/my-feature"},
  "members": [
    {"name": "app", "worktree": "/home/me/workspaces/my-feature/app", "origin": "https://github.com/me/app"},
    {"name": "libfoo", "worktree": "/home/me/workspaces/my-feature/libfoo", "origin": "https://github.com/me/libfoo"}
  ],
  "config": {}
}
```

The answer:

```json
{
  "files": [{"path": ".tandem/zig/forks.args", "content": "--fork=../../libfoo\n"}],
  "stale": [],
  "links": [],
  "warnings": []
}
```

Rules:

1. A plugin may read files in the member worktrees. It must not write any file. Tandem writes the
   files and links of the plan.
2. Tandem checks each path in the plan with the same rules as for built-in generators: inside the
   space root, no `..`, and only Meson-style links into a worktree.
3. The time limit is 60 seconds, and the output limit is 16 MiB. A non-zero exit or a bad JSON
   object is a failed saga step, so Tandem rolls back.
4. Tandem refuses a protocol value that it does not know, and tells you which versions it supports.
5. stderr goes to the user, with the plugin ID before each line.
6. `tdm plugin check <id>` runs meta, then plan on a test space, and validates both answers against
   the JSON Schemas in docs/plugins.md.

### Why not other plugin methods

| Method | Why not |
|---|---|
| Go plugin package | Linux and macOS only. The plugin must use the same Go version and build flags as the host. It breaks after every Tandem update. |
| gRPC (hashicorp/go-plugin) | Good for long-running plugins. Tandem makes one call for each plan, so a process and JSON are enough. |
| WebAssembly (wazero) | Gives a sandbox. It is a good later step if plugins from other people become common. Version 1 keeps the simple method. |

examples/plugins/ has a Zig plugin in shell and a Bundler plugin in Python. They are also test
fixtures for the external package.

## Makefile

The Makefile is the one entry point for people, CI and agents. make alone prints the help. make
check runs what CI runs, except the toolchain tests. The Makefile in the repo is the current
version; it has strict bash, .ONESHELL, .DELETE_ON_ERROR, --warn-undefined-variables, no built-in
rules, `## text` help comments, `$(call need,tool)`, VERSION/COMMIT/DATE from git, and pinned Go
tools through `go tool -modfile=go.tool.mod`.

## Nix

One flake gives the dev tools, the package, an overlay, a NixOS module and a home-manager module.

| Output | Use |
|---|---|
| packages.<system>.default | nix build, nix profile install github:OWNER/tandem |
| overlays.default | Adds pkgs.tandem to your nixpkgs |
| devShells.<system>.default | Go, gopls, golangci-lint, gofumpt, goreleaser, nixfmt, taplo |
| devShells.<system>.integration | The default shell plus the toolchains for make test-integration |
| nixosModules.default | programs.tandem for a NixOS system |
| homeManagerModules.default | programs.tandem for one user, with typed settings |
| checks.<system> | The package build with its tests, and a nixfmt check |
| formatter.<system> | nix fmt |

Rules:

1. Go version. The package uses buildGoLatestModule, and the dev shell uses go_latest. The dev shell
   sets GOTOOLCHAIN=local, so Go never downloads a different toolchain.
2. One version source. internal/version/VERSION holds the version (for example 0.1.0). Go embeds
   it, and the flake reads it with lib.fileContents. The flake adds the short git revision.
3. vendorHash. After each change to go.mod, set vendorHash = lib.fakeHash, run nix build, and copy
   the hash from the got: line. make nix-vendor-hash prints these steps. Because tools are in
   go.tool.mod, a tool update does not change vendorHash.
4. Small source. lib.fileset gives the build only go.mod, go.sum, cmd, internal and schema. A
   change to the docs does not cause a rebuild.
5. No go generate in the build. Generated files are committed, and CI checks them.
6. git on PATH. The wrapper adds Nix git to the end of PATH. Your own git comes first, with your
   configuration and credential helpers.
7. System config. The NixOS module writes /etc/xdg/tandem/config.toml. For this, Tandem reads
   config files in this order, and a later file overrides an earlier one: each directory in
   $XDG_CONFIG_DIRS (default /etc/xdg), then $XDG_CONFIG_HOME/tandem/config.toml, then TDM_CONFIG
   or --config. This is a change to the config spec.
8. Impermanence. On a system with an impermanent home, persist ~/.local/share/tandem. It holds the
   space state.

.envrc has one line, `use flake`, so direnv loads the default shell when you cd into the repo. Use
`nix develop .#integration` for the toolchain tests.

### How to use it

```nix
# flake.nix of your NixOS or home-manager configuration
inputs.tandem = {
  url = "github:OWNER/tandem";
  inputs.nixpkgs.follows = "nixpkgs";
};

# NixOS: system-wide
imports = [ inputs.tandem.nixosModules.default ];
programs.tandem.enable = true;

# home-manager: for one user, with config
imports = [ inputs.tandem.homeManagerModules.default ];
programs.tandem = {
  enable = true;
  settings = {
    discovery.root_dir = "~/repos";
    spaces.root_dir = "~/workspaces";
    generate.enabled = [ "go" "rust" "js" "cmake" "meson" ];
  };
};

# Only the package, or through the overlay
environment.systemPackages = [ inputs.tandem.packages.${pkgs.stdenv.hostPlatform.system}.default ];
nixpkgs.overlays = [ inputs.tandem.overlays.default ];   # then pkgs.tandem
```

Without a configuration: `nix run github:OWNER/tandem -- status` or
`nix profile install github:OWNER/tandem`.

## CI

CI runs the same make targets in the same Nix dev shell that you use. Thus a pass on your machine
is a pass in CI.

| Job | Runs | When | Locks |
|---|---|---|---|
| check | nix develop -c make check | Each push and PR | Generated files, tidy modules, format, vet, lint (depguard), tests, testscripts |
| race | nix develop -c make test-race vuln | Each push and PR | Data races, known vulnerabilities |
| nix | nix flake check -L | Each push and PR (Linux), plus a macOS build | The package builds and its tests pass; Nix files are formatted |
| integration | nix develop .#integration -c make test-integration | Nightly, and on PRs with the integration label | The nine toolchain checks in the Generators tab |
| release | goreleaser release --clean | Tag v* | Archives, checksums, changelog |

### The layout test

One Go test locks the tree. internal/layout_test.go lists the top-level entries with git ls-files
and compares them with an allowlist that is the same as the Locked project structure section. It
fails on an entry that is not in the list. It also checks that each directory under internal/gen/
(except all, external, gentest, urlnorm) has <id>.go, <id>_test.go, doc.go and testdata/. To add a
top-level entry, change this tab, then the allowlist, in the same PR.

### Workflow

```yaml
# .github/workflows/ci.yml
name: CI
on:
  push: { branches: [main] }
  pull_request:
  schedule: [{ cron: "17 6 * * *" }]   # nightly integration

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: cachix/install-nix-action@v31   # pin to a commit SHA
      - run: nix develop -c make check

  race:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: cachix/install-nix-action@v31
      - run: nix develop -c make test-race vuln

  nix:
    strategy:
      matrix: { os: [ubuntu-latest, macos-latest] }
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v6
      - uses: cachix/install-nix-action@v31
      - run: nix flake check -L

  integration:
    if: github.event_name == 'schedule' || contains(github.event.pull_request.labels.*.name, 'integration')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: cachix/install-nix-action@v31
      - run: nix develop .#integration -c make test-integration
```

Dependabot keeps updating gomod and github-actions, as it does in wtg. A weekly job updates
flake.lock with a PR, so the Nix tool versions also move forward in reviewed steps.

The release job and .goreleaser.yaml are a later step. The snapshot target is ready for them.
