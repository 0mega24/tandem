# Multi-language workspace generators (spec)

Copied from the owner's design document, tab "wtg: multi-language workspace generators"
(2026-11-17, @0mega24). Read wtg as tdm for the command and Tandem for the project (see
docs/spec/project.md, naming table): `.wtg/` is `.tandem/`, `WTG_*` is `TDM_*`, "Generated by wtg"
is "Generated by tandem", `<file>.wtg-bak` is `<file>.tandem-bak`, `wtg-<space>` names are
`tandem-<space>`, and `internal/cmd` is `internal/cli` (with the operations in `internal/space`).

## Summary

This spec replaces the Go-only go.work step with a set of workspace generators. Each generator
connects the repos of one space for one build system. The first release supports Go, Rust,
TypeScript and JavaScript, Java and Kotlin, C#, C and C++, and Python (off by default). A second
release adds Haskell, an editor workspace file, and user-defined generators.

"Must" is a requirement. "Should" is a recommendation.

## Goals

1. When you make a space with `wtg new`, wtg writes the correct workspace files for each language
   that it finds in the repos.
2. A build tool that you run in one worktree uses the local source of the other worktrees in the
   space. Go already works this way with go.work.
3. wtg add, wtg remove and wtg delete keep the generated files correct, as they do for go.work now.
4. wtg never writes into a repo worktree for this feature. It writes only into the space root. The
   one exception is the Meson generator, which makes git-ignored symlinks (see its section).
5. wtg does not need a language toolchain to generate files. go.work is written in pure Go, not by
   the go binary.
6. A new language is one new Go package that implements one interface.

## Non-goals

- wtg does not build, install or lock dependencies.
- wtg does not change the manifests in a repo (Cargo.toml, package.json, .csproj and others).
- wtg does not change global tool state, for example `conan editable add` or `pnpm link --global`.
  A hook script can do this (see always.run).
- wtg does not solve version conflicts between repos. If a build tool refuses a local override, wtg
  shows the reason from the plan but does not fix it.

## Current wtg behavior (for reference)

In wtg the Go logic is in five places (workspace.go: detectGoMods, detectGoVersion, goWorkStep,
writeGoWork; new.go adds goWorkStep when a repo has go.mod; add.go writes go.work again; remove.go
writes go.work again or deletes it, and always deletes go.work.sum; delete.go deletes go.work and
go.work.sum; state.go has `GoWorkspace bool` (`go_workspace`)). Three facts:

- Detection read the main clone. The new design reads the worktree after the saga makes it.
- Detection is root-only. A multi-module Go repo gets one use line.
- Symlinked always.repos are skipped. The new design keeps this rule for all generators.

## Prior art

- reporoot makes npm workspaces, go.work, uv workspaces, gita config and a VS Code workspace for a
  set of repos. Each integration finds its repos by manifest and does nothing if the tool is not
  installed.
- repoweave has npm, pnpm, Go, uv and Cargo integrations. Each one is a Rust module that implements
  one trait (activate, deactivate, check, generated_files). Before it deletes a Cargo.toml, it
  makes sure that the file starts with its generated header.

wtg takes three ideas: one interface per ecosystem, a list of generated files, and an ownership
check before a delete. It adds rules for repos that are already workspaces.

### Standard mechanism per ecosystem

| Ecosystem | Standard mechanism | Effect |
|---|---|---|
| Go | go.work with use | Local modules replace module versions |
| Rust | [patch] in .cargo/config.toml | A local crate replaces the registry or git crate |
| JS / TS (pnpm) | pnpm-workspace.yaml | All matched packages are one workspace |
| JS / TS (npm, Yarn, Bun) | workspaces in a root package.json | Same as pnpm |
| Java / Kotlin (Gradle) | includeBuild in a root settings file | Gradle replaces module dependencies with the included build |
| Java (Maven) | Aggregator pom.xml with <modules> | The reactor builds modules in dependency order |
| C# / .NET | Solution file (.slnx) | One solution for IDE and dotnet build; no dependency swap |
| C / C++ (CMake) | FETCHCONTENT_SOURCE_DIR_<NAME> | FetchContent uses a local directory and does not download |
| Python (uv) | [tool.uv.workspace] | One lock, editable members |
| Haskell (Cabal) | cabal.project with packages: | Local packages are built in place |
| Any editor | .code-workspace with folders | One window, one root per repo |

### The main risk: nested workspaces

A root aggregator file can break a repo that is already a workspace. Cargo stops with "multiple
workspace roots found" when a workspace member is also a workspace root. It also stops with
"current package believes it's in a workspace when it's not" when a parent Cargo.toml has a
[workspace] that does not list the package. For this reason the Rust generator writes a root
[workspace] only when no member is a workspace. In all other cases it uses [patch].

## Architecture

A new package, internal/gen, holds one Generator interface and a registry. Each language is a
sub-package (internal/gen/golang, internal/gen/rust, and so on). The commands call the registry.
They do not call a language package directly.

### Interface

(The project spec replaces `ID()` and `DefaultEnabled()` with `Meta()`, and adds `Links` to Plan.)

```go
package gen

// Member is one feature-branch worktree in the space.
// Symlinked always.repos are never Members.
type Member struct {
    Name         string // short name, e.g. "myorg/api"
    WorktreePath string // absolute
    RepoPath     string // main clone, absolute
    OriginURL    string // from git remote get-url origin
}

// Space is the input to Plan.
type Space struct {
    Name, Root, Branch string
    Members            []Member
    Config             map[string]any // [generate.<id>] table
}

// Detection is what one generator found in one Member.
type Detection struct {
    Member   Member
    Manifest string         // relative path, e.g. "Cargo.toml"
    Facts    map[string]any // names, versions, members, sources
}

type File struct {
    Path    string // relative to the space root
    Content []byte
}

type Plan struct {
    Files    []File   // files to write
    Stale    []string // derived files to delete, e.g. "go.work.sum"
    Warnings []string // shown to the user; never fatal
}

type Generator interface {
    ID() string                 // "go", "rust", "js", ...
    DefaultEnabled() bool
    Detect(m Member) (*Detection, error) // nil, nil = not this language
    Plan(s Space, found []Detection) (Plan, error) // pure: no I/O
}
```

### Rules for every generator

1. Detect must only read files in the worktree. It must not run a subprocess.
2. Plan must be a pure function. It must not read or write files.
3. Plan must give the same bytes for the same input. Sort members by short name. Use / in paths.
   Write paths relative to the space root, with a ./ prefix where the format allows.
4. Every file must start with the ownership header when the format has comments: `Generated by wtg
   for space <name>. Do not edit. Run 'wtg generate <name>' to update.` JSON has no comments. For
   JSON files, the state file hash is the only ownership record.
5. A generator must return an empty Plan when no members match. It must not return an error for this.
6. A generator must not write a file outside the space root, and must not write into a member
   worktree. The one exception is the Meson generator.

### How the commands use it

The write is one saga step for each generator, so the rollback rules apply. The order in `wtg new`:

1. Pre-flight checks.
2. Saga: make worktrees and symlinks.
3. Saga: run Detect for each enabled generator on each Member. This reads the new worktrees, not
   the main clones.
4. Saga: run Plan, then do the ownership check. Then write the files. Undo puts back the old
   content, or deletes a new file.
5. Save state, with the list of generated files and their SHA-256 hashes.
6. Run the always.run hook. A new variable, WTG_GENERATED_FILES, gives the generated paths, one on
   each line.

wtg add and wtg remove do steps 3 to 5 for the full new member set. wtg delete deletes the files in
the state list that it owns, and their Stale files.

## Detection rules

Detection finds the root manifest of a repo, then reads the members that the manifest itself
declares. wtg does not walk the full tree, except for C#.

1. Root first. Each generator looks for its manifest at the worktree root.
2. Use the repo's own member list. When the root manifest declares members (Cargo [workspace]
   members, pnpm-workspace.yaml, package.json workspaces, Maven <modules>, uv members), the
   generator expands those globs inside the worktree. It must not guess members that the repo does
   not declare.
3. Limited depth. The detect_depth setting (default 0, root only) lets a generator also look in
   sub-directories. The scan must skip .git, node_modules, target, build, bin, obj, dist, vendor,
   .venv and every directory in .gitignore.
4. One repo, many languages. A repo can match more than one generator.
5. One language, many build systems. When one repo matches two build systems of one language (for
   example, pom.xml and build.gradle), the generator uses the order in its table and gives a warning.
6. Symlinks are not members. Symlinked always.repos are skipped.
7. No match is not an error. When no member matches, the generator writes nothing, and it deletes
   the files that it wrote before.

C# is the exception to rule 1. The C# generator uses the solution file at the repo root when there
is one. If there is no solution file, it scans for *.csproj, *.fsproj and *.vbproj to a depth of 4.

### Go (go)

- go.work gets a use line for each member with a root go.mod.
- The go line is the highest go directive of the members. The fallback is 1.21.
- Stale is go.work.sum. wtg deletes it when the member set changes.

### Rust (rust)

Three modes; the default is auto. In auto mode, wtg picks the mode for each space:

- No member has a [workspace] table: workspace mode.
- One or more members have a [workspace] table: patch mode.

wtg picks again at each add, remove and generate. When the mode changes, wtg deletes the files of
the old mode and their Stale paths, then writes the files of the new mode. `wtg new` and
`wtg generate --dry-run` show the selected mode and the reason. `generate.rust.mode` set to patch
or workspace turns auto off.

**Mode patch.** wtg writes `<space>/.cargo/config.toml`. Cargo reads .cargo/config.toml in each
parent directory of the current directory, so a cargo build in any worktree finds this file.

```toml
# Generated by wtg for space my-feature. Do not edit.
# Run 'wtg generate my-feature' to update.

[patch.crates-io]
shared-core = { path = "shared/crates/core" }
shared-macros = { path = "shared/crates/macros" }

[patch."https://github.com/myorg/shared"]
shared-core = { path = "shared/crates/core" }
```

Rules:

1. For each member, read [package].name. If the root has [workspace].members, expand the globs and
   read each member crate name too.
2. Add each crate to [patch.crates-io]. Add each crate to the registries in
   generate.rust.registries too.
3. Read the `git = "..."` dependencies of every member. When a git URL is the same as the origin
   URL of another member, add a [patch."<url>"] table for the crates of that member. Compare URLs
   after normalization: remove .git, the trailing /, and the scheme difference between git@host:
   and https://host/.
4. Do not add a member's own crates to a patch that only that member uses (Cargo "unused patch").
5. Write paths relative to the space root. Open item: an integration test must prove the path base
   for [patch] in a config file. If the test fails, write absolute paths.

Limits: Cargo uses a patch only when the local version agrees with the version requirement. A cargo
build in a worktree updates that worktree's Cargo.lock with the patched sources; do not commit
this. `wtg status --long` shows it as a changed file.

**Mode workspace.** wtg writes a virtual workspace `<space>/Cargo.toml` with resolver = "2" and one
member for each crate. All members share one Cargo.lock and one target/ in the space root. If this
mode is set in the config and a member has a [workspace] table, wtg uses patch mode for that space
and gives a warning. Stale: Cargo.lock and target/ in the space root.

### JavaScript and TypeScript (js)

The package manager of each member comes from the packageManager field in package.json. If that
field is missing, from the lockfile: pnpm-lock.yaml is pnpm, yarn.lock is Yarn, bun.lock or
bun.lockb is Bun, package-lock.json is npm.

- All members have the same manager: wtg writes the file for that manager.
- Members have different managers: wtg uses generate.js.manager. If that value is auto, wtg writes
  nothing and gives a warning with the list of managers.

For pnpm, wtg writes pnpm-workspace.yaml with `linkWorkspacePackages: true` (since pnpm 9 it is
false by default, so registry-version dependencies between repos would not link):

```yaml
# Generated by wtg for space my-feature. Do not edit.
packages:
  - ./api
  - ./frontend
  - ./shared/packages/*   # from shared/pnpm-workspace.yaml
linkWorkspacePackages: true
```

For npm, Yarn and Bun, wtg writes a root package.json:

```json
{
  "name": "wtg-my-feature",
  "private": true,
  "workspaces": ["./api", "./frontend", "./shared/packages/*"]
}
```

Rules:

1. When a member is a workspace itself, wtg copies its member globs with the member path as a
   prefix. It does not list the member's root package as a second workspace root.
2. You run the install command from the space root.
3. Stale is the root lockfile (pnpm-lock.yaml, package-lock.json, yarn.lock, bun.lock) and the root
   node_modules/.

### TypeScript project references (ts, off by default)

Writes a solution-style `<space>/tsconfig.json` with `"files": []` and one references entry for
each member tsconfig.json that has `compilerOptions.composite: true`. Then `tsc --build` from the
space root builds all members in order.

### Java and Kotlin with Gradle (gradle)

wtg writes `<space>/settings.gradle.kts` with one includeBuild for each Gradle member.

```kotlin
// Generated by wtg for space my-feature. Do not edit.
rootProject.name = "wtg-my-feature"

includeBuild("api")
includeBuild("myorg/shared")
```

Rules:

1. A member is a Gradle build when it has settings.gradle, settings.gradle.kts, build.gradle or
   build.gradle.kts at its root.
2. A member without a settings file gets a warning: tell the user to add a settings file to the repo.
3. The substitution applies only when you run Gradle from the space root. Use the wrapper of one
   member: `./api/gradlew -p . build`.
4. Do not include a Maven member here.
5. Stale is .gradle/ and build/ in the space root.

### Java with Maven (maven)

wtg writes an aggregator `<space>/pom.xml` with packaging pom and one <module> for each Maven member.

```xml
<!-- Generated by wtg for space my-feature. Do not edit. -->
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>wtg.local</groupId>
  <artifactId>wtg-my-feature</artifactId>
  <version>0</version>
  <packaging>pom</packaging>
  <modules>
    <module>api</module>
    <module>myorg/shared</module>
  </modules>
</project>
```

Rules:

1. The aggregator is not a parent. Members keep their own <parent>.
2. wtg must not make a .mvn/ directory in the space root (Maven 4 looks up the tree for .mvn).
3. A repo with pom.xml and a Gradle build file is a member of both plans, and gets a warning.

### C# and .NET (dotnet)

wtg writes `<space>/<space-name>.slnx`. One solution folder holds the projects of each member.

```xml
<!-- Generated by wtg for space my-feature. Do not edit. -->
<Solution>
  <Folder Name="/api/">
    <Project Path="api/src/Api/Api.csproj" />
    <Project Path="api/tests/Api.Tests/Api.Tests.csproj" />
  </Folder>
  <Folder Name="/shared/">
    <Project Path="shared/src/Shared/Shared.csproj" />
  </Folder>
</Solution>
```

Rules:

1. When a member has one .slnx or .sln at its root, take the project list from it.
2. When a member has no solution file, scan for project files (see Detection rules).
3. `generate.dotnet.format = "sln"` writes the old .sln format. Use deterministic project GUIDs
   (UUIDv5 of the relative path).

Limit: a solution does not change a PackageReference into a ProjectReference.

### C and C++ with CMake (cmake)

wtg writes an initial-cache script, `<space>/.wtg/cmake/overrides.cmake`, given to CMake with -C:

```cmake
# Generated by wtg for space my-feature. Do not edit.
set(FETCHCONTENT_SOURCE_DIR_SHARED "/home/me/workspaces/my-feature/shared" CACHE PATH "wtg")
set(CPM_shared_SOURCE "/home/me/workspaces/my-feature/shared" CACHE PATH "wtg")
```

`cmake -S api -B build/api -C .wtg/cmake/overrides.cmake`

Rules:

1. The variable name comes from the consumer, not from the dependency. wtg reads the CMake files
   of each member (CMakeLists.txt and *.cmake, depth 3) for
   `FetchContent_Declare(<name> ... GIT_REPOSITORY <url>)` and
   `CPMAddPackage(NAME <name> GIT_REPOSITORY <url>)`.
2. When <url> is the same as the origin URL of another member (normalized as for Rust), wtg adds
   the two set lines for that member.
3. Use absolute paths (CMake issue 21624).
4. wtg does not parse find_package.
5. Bazel, Make, Conan editable mode and vcpkg overlays are out of scope for release 1.

### C and C++ with Meson (meson)

Meson finds subprojects only in the subprojects directory at its own top level. When a subproject
directory is already there, Meson uses it as it is. So the Meson generator is the one exception to
goal 4: it makes a symlink in the consumer worktree that points to the dependency worktree:

```
~/workspaces/my-feature/
  app/
    subprojects/
      libfoo.wrap              ← in the repo: [wrap-git] url = https://github.com/myorg/libfoo.git
      libfoo -> ../../libfoo   ← symlink made by wtg
  libfoo/                      ← worktree on the feature branch
```

Rules:

1. A member is a Meson project when it has meson.build at its root.
2. For each Meson member, read subprojects/*.wrap. Take the url of a [wrap-git] section. Take the
   link name from the directory key, or the wrap file name without .wrap.
3. When the url is the same as the origin URL of another member (normalized), plan a link
   subprojects/<directory> to that member, with a relative target.
4. Do this for transitive dependencies too.
5. Make a link only when the path subprojects/<directory> does not exist (else warn: delete that
   directory), and `git check-ignore` says that the path is ignored in the consumer worktree (else
   warn and do not make the link).
6. wtg must not change .gitignore or .git/info/exclude.
7. wtg remove and wtg delete delete the links of a member before they remove its worktree.

Changes: Plan gets `Links []Link` (`Link{Path, Target string}`, Path relative to the space root).
The git check-ignore call is in the apply step and uses the git Runner. The state file records each
link as a GeneratedFile with the link target in place of SHA256; the ownership check compares the
target; wtg deletes a path only when it is still a symlink to the same target. [wrap-file] is skipped.

### Python with uv (uv, release 1, off by default)

wtg writes a virtual workspace root `<space>/pyproject.toml` with [tool.uv.workspace] members and
one `{ workspace = true }` source for each member package. When a member is a uv workspace itself,
wtg copies its member globs with the member path as a prefix. Stale is uv.lock and .venv/.

### Haskell with Cabal (cabal, release 2)

wtg writes `<space>/cabal.project` with a packages: list. When a member has its own cabal.project,
wtg copies its package locations with the member path as a prefix. Stale is dist-newstyle/.

### Editor workspace (vscode, release 2, off by default)

wtg writes `<space>/<space-name>.code-workspace` with one folders entry for each member and each
symlinked repo. wtg owns only the folders key; it keeps the other keys when it writes the file again.

### Custom generators

Replaced by the plugin protocol (docs/spec/project.md, "External generator plugins").

## Configuration

A new [generate] table goes in config.toml. All keys are optional. With no [generate] table, wtg
uses the default-on generators. `wtg config init` writes this table as comments, with the defaults.

```toml
[generate]
# Generators to use. Omit to use the defaults. "none" turns all generators off.
enabled = ["go", "rust", "js", "gradle", "maven", "dotnet", "cmake", "meson"]
detect_depth = 0          # 0 = worktree root only

[generate.rust]
mode = "auto"             # "auto" | "patch" | "workspace"
registries = []           # extra registries to patch, besides crates-io

[generate.js]
manager = "auto"          # "auto" | "pnpm" | "npm" | "yarn" | "bun"
link_workspace_packages = true   # pnpm only

[generate.dotnet]
format = "slnx"           # "slnx" | "sln"

[generate.cmake]
scan_depth = 3
```

Rules:

1. An unknown generator ID in enabled is a config error. wtg shows the list of known IDs.
2. A plugin id must not be the same as a built-in ID.
3. The YAML config gets the same keys under generate:, because the parser follows the file extension.
4. There is no per-space config file. A flag on wtg new changes the set for one space, and wtg
   records that set in the state file.

## Commands and flags

| Command | Change |
|---|---|
| wtg new | New flags --generate=<ids> (comma list, or none) and --no-generate. The result goes in the state file. |
| wtg add | Uses the generator set from the state file. Writes the files again for the full new member set. |
| wtg remove | Same as add. When a generator has no members left, wtg deletes its files and its Stale files. |
| wtg delete | Deletes all owned generated files and their Stale files. |
| wtg generate <space> (new) | Runs detection and writes the files again for the current members. |
| wtg generate <space> --dry-run | Shows the plan: each file, the members it uses, the warnings, and a diff against the current file. Writes nothing. |
| wtg generate <space> --force | Writes a file that is not owned by wtg. The old file is copied to <file>.wtg-bak first. |
| wtg status --long | Shows the generated files of each space, and marks a file that a person changed. |

Example output of `wtg new`:

```
$ wtg new my-feature api shared frontend
  api       ✓ worktree  [geoff/my-feature]
  shared    ✓ worktree  [geoff/my-feature]
  frontend  ✓ worktree  [geoff/my-feature]
  go        ✓ go.work                (api, shared)
  rust      ✓ .cargo/config.toml     (shared → api: 2 crates)
  js        ✓ pnpm-workspace.yaml    (frontend, shared/packages/*)
  cmake     - no members
✓ space "my-feature" created
```

The skills and README.md must list the generators.

## State, ownership and cleanup

### Schema

```go
type Space struct {
    Name       string
    Path       string
    Branch     string
    CreatedAt  time.Time
    Repos      []RepoEntry
    Generators []string        `yaml:"generators,omitempty"` // set used for this space
    Generated  []GeneratedFile `yaml:"generated,omitempty"`

    // Deprecated: read for old state files only. Not written.
    GoWorkspace bool `yaml:"go_workspace,omitempty"`
}

type GeneratedFile struct {
    Generator string   `yaml:"generator"` // "rust"
    Path      string   `yaml:"path"`      // ".cargo/config.toml", relative to Space.Path
    SHA256    string   `yaml:"sha256"`    // hash of the bytes that wtg wrote
    Stale     []string `yaml:"stale,omitempty"`
}
```

### Migration

When a state file has `go_workspace: true` and no generated list, make one GeneratedFile for
go.work with `Stale: [go.work.sum]`, with the hash from the file on disk. Generators becomes the
current default set. The new format is written at the next save.

### Ownership check (before each write or delete)

| File on disk | In state? | Hash same? | Action |
|---|---|---|---|
| Missing | Any | — | Write it |
| Present | Yes | Yes | Write it again or delete it |
| Present | Yes | No | A person changed it. Skip it and give a warning. --force writes it |
| Present | No | — | Not owned. Skip it and give a warning. --force writes it |

For vscode, compare only the folders key.

### Cleanup

- wtg delete deletes each owned file, then each Stale path of that file. A Stale directory is
  deleted only when it is in the space root and is not a member worktree.
- An empty directory that wtg made (.cargo/, .wtg/cmake/) is deleted.
- A failure to delete is a warning, not an error.
- Auto-heal also checks generated files. A file in state but not on disk is removed from state
  with a warning.

## Testing

1. Golden-file unit tests (each generator): testdata/<case>/ with an input tree and an expected
   output. `go test ./... -update` writes the expected files again. Required cases:
   - no members
   - one member
   - two members, one depends on the other
   - a member that is already a workspace (nested)
   - a symlinked always.repos entry (must be skipped)
   - mixed build systems or package managers (must give a warning)
2. Command tests (no toolchain): all generated files, rollback (a failure after the generator step
   puts back the old files), the ownership table, --force, the go_workspace migration, and
   generate --dry-run.
3. Toolchain integration tests (optional; skip when the tool is not on PATH):

| Generator | Check command | Pass condition |
|---|---|---|
| go | go list -m all | Shows the local module paths |

## Phased delivery

toolchain checks pass in CI. Each phase adds its own CHANGELOG.md entries under `## [Unreleased]`.

## Language coverage

12 of the 25 most used languages (Stack Overflow Developer Survey 2026) have a built-in generator.
Candidates with a local-override mechanism outside the repo files:

1. Bazel: `--override_module=<name>=<path>` in `<space>/.wtg/bazel/overrides.bazelrc`.
2. Ruby (bundler): `BUNDLE_LOCAL__<GEM>` variables in `<space>/.wtg/env`. Bundler stops if the
   Gemfile branch is not the worktree branch, so the generator must check this.
3. Zig: an arguments file with one `zig build --fork=<path>` for each member.
4. Nix: `--override-input <input> path:<dir>` arguments file; match inputs by URL; absolute paths.
5. Dart (pub): pub workspace with pubspec_overrides.yaml in the worktree. Risk: pub get deletes the
   members' pubspec.lock files.

PHP, Swift, Elixir, Lua, R, Perl, MATLAB, GDScript: hooks only (each mechanism changes a repo file
or has no dependency graph).
